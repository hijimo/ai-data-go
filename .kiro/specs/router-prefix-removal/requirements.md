# 需求文档

## 简介

统一项目中所有 API 路由的 `@Router` 注解格式，移除 `/api/v1` 前缀，使路由路径更加简洁统一。

## 术语表

- **@Router 注解**: Swagger/Swaggo 文档生成工具使用的注解，用于标识 API 路由路径和 HTTP 方法
- **路由前缀**: API 路径中的版本标识符，如 `/api/v1`
- **Handler**: Go HTTP 处理器函数，负责处理特定路由的请求

## 需求

### 需求 1

**用户故事:** 作为开发人员，我希望所有 API 路由注解格式统一，以便维护和理解 API 结构

#### 验收标准

1. 当扫描项目中的所有 Go 文件时，系统应该识别出所有包含 `@Router` 注解的文件
2. 当检查 `@Router` 注解时，系统应该识别出包含 `/api/v1` 前缀的路由路径
3. 当修改 `@Router` 注解时，系统应该移除 `/api/v1` 前缀但保留其余路径部分
4. 当修改完成后，系统应该确保所有 `@Router` 注解不再包含 `/api/v1` 前缀
5. 当修改完成后，系统应该保持 HTTP 方法标识符（如 `[get]`、`[post]`）不变

### 需求 2

**用户故事:** 作为开发人员，我希望修改后的代码能够正常编译和运行，以便不影响现有功能

#### 验收标准

1. 当修改 `@Router` 注解后，系统应该确保 Go 代码能够正常编译
2. 当修改 `@Router` 注解后，系统应该确保路由注册逻辑与新的路径格式匹配
3. 当修改 `@Router` 注解后，系统应该确保 Swagger 文档能够正确生成
4. 当运行项目时，系统应该能够正常启动并响应 API 请求

### 需求 3

**用户故事:** 作为开发人员，我希望了解哪些文件被修改了，以便进行代码审查

#### 验收标准

1. 当修改完成后，系统应该提供被修改文件的清单
2. 当修改完成后，系统应该显示每个文件中修改的具体内容
3. 当修改完成后，系统应该统计总共修改的 `@Router` 注解数量
