# 多租户用户管理与 JWT 身份认证需求文档

## 简介

本文档定义了一个支持多租户隔离的用户管理与 JWT 身份认证系统的需求。该系统将为 Go/Gin/GORM 应用提供完整的身份认证、授权和租户隔离能力，支持 JWT access token 和 refresh token 机制，实现基于角色的访问控制（RBAC），并提供安全的密码管理和 token 生命周期管理。

## 术语表

- **系统**：多租户用户管理与 JWT 身份认证系统
- **租户（Tenant）**：独立的客户或组织实体，拥有独立的用户和数据空间
- **用户（User）**：隶属于某个租户的系统使用者
- **Access Token**：短期有效的 JWT 令牌，用于 API 访问授权
- **Refresh Token**：长期有效的不透明令牌，用于获取新的 Access Token
- **RBAC**：基于角色的访问控制（Role-Based Access Control）
- **租户标识符**：用于识别租户的信息，可以是子域名、请求头、URL 参数或 Cookie
- **Token 轮换**：使用 Refresh Token 后立即替换为新 Token 的安全机制
- **Token 撤销**：使 Token 失效的操作，通常用于注销或安全事件

## 需求

### 需求 1：租户管理

**用户故事：** 作为系统管理员，我希望能够创建和管理多个租户，以便为不同的客户提供独立的服务空间

#### 验收标准

1. 当系统管理员提交租户创建请求时，系统应该创建一个新的租户记录，包含唯一标识符、名称、域名和元数据
2. 当系统管理员查询租户列表时，系统应该返回所有租户的基本信息和状态
3. 当系统管理员更新租户信息时，系统应该验证数据有效性并更新租户记录
4. 当系统管理员禁用租户时，系统应该将租户状态设置为禁用，并阻止该租户下所有用户的访问
5. 当系统管理员删除租户时，系统应该执行软删除操作，标记租户为已删除状态

### 需求 2：用户注册与管理

**用户故事：** 作为租户管理员，我希望能够为我的租户创建和管理用户账户，以便控制谁可以访问系统

#### 验收标准

1. 当租户管理员提交用户注册请求时，系统应该验证邮箱在该租户内的唯一性，并使用 bcrypt 或 argon2 算法对密码进行哈希处理后存储
2. 当用户注册成功时，系统应该创建用户记录，包含租户 ID、邮箱、密码哈希、显示名称和默认角色
3. 当租户管理员查询用户列表时，系统应该仅返回该租户下的用户信息
4. 当租户管理员更新用户信息时，系统应该验证操作权限并更新用户记录
5. 当租户管理员禁用用户时，系统应该将用户状态设置为非活跃，并撤销该用户的所有有效 Token

### 需求 3：用户登录与身份认证

**用户故事：** 作为用户，我希望能够使用邮箱和密码登录系统，以便访问我有权限的功能

#### 验收标准

1. 当用户提交登录请求时，系统应该验证租户标识符、邮箱和密码的正确性
2. 当用户凭证验证成功时，系统应该生成一个包含用户 ID、租户 ID、角色和权限范围的 Access Token（JWT），有效期为 60 分钟
3. 当用户凭证验证成功时，系统应该生成一个 Refresh Token，将其哈希值存储到数据库，有效期为 7-30 天
4. 当用户登录成功时，系统应该返回 Access Token 和 Refresh Token，并记录登录审计日志
5. 当用户提供错误的凭证时，系统应该返回认证失败错误，并记录失败审计日志

### 需求 4：Token 刷新机制

**用户故事：** 作为用户，我希望在 Access Token 过期后能够自动获取新的 Token，以便无需重新登录即可继续使用系统

#### 验收标准

1. 当用户提交 Token 刷新请求时，系统应该验证 Refresh Token 的存在性、有效性和未撤销状态
2. 当 Refresh Token 验证通过时，系统应该生成新的 Access Token 和新的 Refresh Token
3. 当生成新的 Refresh Token 时，系统应该将旧的 Refresh Token 标记为已撤销，并记录 replaced_by 字段指向新 Token
4. 当 Refresh Token 已过期或已撤销时，系统应该拒绝刷新请求并返回错误
5. 当 Token 刷新成功时，系统应该返回新的 Access Token 和 Refresh Token

### 需求 5：用户注销

**用户故事：** 作为用户，我希望能够安全地退出系统，以便保护我的账户安全

#### 验收标准

1. 当用户提交注销请求时，系统应该验证用户的身份和 Refresh Token
2. 当注销请求验证通过时，系统应该将用户当前的 Refresh Token 标记为已撤销
3. 当注销成功时，系统应该记录注销审计日志，包含用户 ID、租户 ID、IP 地址和时间戳
4. 当用户注销后尝试使用已撤销的 Refresh Token 时，系统应该拒绝请求并返回错误

### 需求 6：租户隔离与识别

**用户故事：** 作为系统架构师，我希望系统能够自动识别和隔离不同租户的数据，以便确保数据安全和隐私

#### 验收标准

1. 当 API 请求到达时，系统应该从子域名、请求头、URL 参数或 Cookie 中提取租户标识符
2. 当租户标识符提取成功时，系统应该将租户 ID 注入到请求上下文中
3. 当执行数据库查询时，系统应该自动在查询条件中添加租户 ID 过滤条件
4. 当用户尝试访问其他租户的数据时，系统应该拒绝请求并返回权限错误
5. 当租户标识符无效或缺失时，系统应该返回租户识别失败错误

### 需求 7：基于角色的访问控制（RBAC）

**用户故事：** 作为租户管理员，我希望能够为用户分配不同的角色和权限，以便实现细粒度的访问控制

#### 验收标准

1. 当创建或更新用户时，系统应该允许分配一个或多个角色（如 user、admin、moderator）
2. 当用户登录时，系统应该将用户的角色信息编码到 Access Token 的 claims 中
3. 当 API 请求需要特定权限时，系统应该从 Access Token 中提取角色信息并验证权限
4. 当用户没有所需权限时，系统应该拒绝请求并返回权限不足错误
5. 当用户角色更新时，系统应该在下次 Token 刷新时更新 Access Token 中的角色信息

### 需求 8：Token 验证与授权中间件

**用户故事：** 作为 API 开发者，我希望有一个统一的中间件来验证和授权请求，以便简化 API 端点的安全实现

#### 验收标准

1. 当 API 请求到达时，系统应该从 Authorization 请求头中提取 Bearer Token
2. 当提取到 Token 时，系统应该验证 JWT 签名、过期时间和必需的 claims（sub、tid、exp）
3. 当 Token 验证通过时，系统应该将用户 ID、租户 ID 和角色信息注入到请求上下文中
4. 当 Token 无效、过期或缺失时，系统应该返回 401 未授权错误
5. 当 Token 有效但用户权限不足时，系统应该返回 403 禁止访问错误

### 需求 9：密码安全管理

**用户故事：** 作为安全工程师，我希望系统能够安全地存储和验证用户密码，以便保护用户账户免受攻击

#### 验收标准

1. 当用户注册或修改密码时，系统应该使用 bcrypt 或 argon2 算法对密码进行哈希处理
2. 当用户登录时，系统应该使用相同的算法验证密码哈希
3. 当密码验证失败时，系统应该返回通用的认证失败错误，不泄露具体失败原因
4. 系统应该永远不存储明文密码
5. 当用户请求修改密码时，系统应该验证旧密码的正确性后才允许设置新密码

### 需求 10：审计日志记录

**用户故事：** 作为安全审计员，我希望系统能够记录所有身份认证相关的操作，以便进行安全审计和问题追踪

#### 验收标准

1. 当用户登录成功时，系统应该记录审计日志，包含用户 ID、租户 ID、IP 地址、User-Agent 和时间戳
2. 当用户登录失败时，系统应该记录审计日志，包含尝试的邮箱、租户 ID、IP 地址和失败原因
3. 当用户刷新 Token 时，系统应该记录审计日志
4. 当用户注销时，系统应该记录审计日志
5. 当 Refresh Token 被撤销时，系统应该记录审计日志，包含撤销原因

### 需求 11：数据库表结构

**用户故事：** 作为数据库管理员，我希望有清晰定义的数据库表结构，以便支持多租户用户管理和身份认证功能

#### 验收标准

1. 系统应该包含 tenants 表，存储租户信息，包含 id、name、domain、metadata、status、created_at、updated_at、created_by 和 is_deleted 字段
2. 系统应该包含 users 表，存储用户信息，包含 id、tenant_id、email、email_verified、phone、password_hash、display_name、is_active、is_admin、roles、meta、last_login_at、created_at、updated_at、created_by 和 is_deleted 字段
3. 系统应该包含 refresh_tokens 表，存储 Refresh Token 信息，包含 id、user_id、tenant_id、token_hash、revoked、created_at、expires_at 和 replaced_by 字段
4. 系统应该包含 auth_audit 表，存储审计日志，包含 id、tenant_id、user_id、event、ip、user_agent、meta 和 created_at 字段
5. 系统应该在 users 表上创建唯一索引 (tenant_id, email)，确保同一租户内邮箱唯一

### 需求 12：JWT Claims 结构

**用户故事：** 作为 API 开发者，我希望 JWT Token 包含标准和自定义的 claims，以便在 API 中进行授权决策

#### 验收标准

1. 当生成 Access Token 时，系统应该包含标准 claims：iss（签发者）、sub（用户 ID）、aud（受众）、exp（过期时间）、iat（签发时间）和 jti（JWT ID）
2. 当生成 Access Token 时，系统应该包含自定义 claim tid（租户 ID）
3. 当生成 Access Token 时，系统应该包含自定义 claim roles（用户角色数组）
4. 当生成 Access Token 时，系统应该包含自定义 claim scopes（权限范围数组）
5. 当验证 Access Token 时，系统应该验证所有必需的 claims 是否存在且有效
