# 需求文档

## 简介

本文档定义了为 Genkit Go 框架创建 Azure AI Provider 插件的需求。该插件将使 Genkit 能够与 Azure OpenAI 服务集成，支持使用 Azure OpenAI 的 Responses API（而非传统的 chat/completions 端点）进行模型调用。

## 术语表

- **Genkit**: Firebase 的 AI 应用开发框架
- **Provider**: Genkit 中的模型提供商插件
- **Azure OpenAI**: Microsoft Azure 提供的 OpenAI 服务
- **Responses API**: Azure OpenAI 的新 API 端点（/openai/responses）
- **Model**: AI 模型的抽象表示
- **Embedder**: 文本嵌入生成器
- **Plugin**: Genkit 的可插拔组件
- **Streaming**: 流式响应模式
- **Tool Call**: 模型调用外部工具的能力

## 需求

### 需求 1

**用户故事**: 作为开发者，我希望能够在 Genkit 中使用 Azure OpenAI 服务，以便利用 Azure 的企业级 AI 能力。

#### 验收标准

1. 当开发者初始化 Azure AI Provider 时，系统应该创建一个有效的 Genkit 插件实例
2. 当开发者提供 API Key 和 Base URL 时，系统应该正确配置 Azure OpenAI 客户端
3. 当开发者注册 Azure AI Provider 时，系统应该将其添加到 Genkit 的插件注册表中
4. 当开发者指定 API 版本参数时，系统应该在请求中包含正确的 api-version 查询参数
5. 当开发者未指定 API 版本时，系统应该使用默认的 API 版本（2025-04-01-preview）

### 需求 2

**用户故事**: 作为开发者，我希望能够定义和使用 Azure OpenAI 模型，以便在应用中进行文本生成。

#### 验收标准

1. 当开发者定义模型时，系统应该创建一个符合 Genkit Model 接口的模型实例
2. 当模型接收生成请求时，系统应该使用 Azure OpenAI Responses API 端点（/openai/responses）
3. 当模型配置包含多模态支持时，系统应该正确处理文本和图像输入
4. 当模型配置包含工具支持时，系统应该正确转换 Genkit 工具定义为 Azure OpenAI 格式
5. 当模型配置包含系统提示时，系统应该在请求中正确设置系统消息

### 需求 3

**用户故事**: 作为开发者，我希望支持流式响应，以便实时获取模型生成的内容。

#### 验收标准

1. 当请求包含回调函数时，系统应该使用流式模式调用 Azure OpenAI API
2. 当接收到流式数据块时，系统应该解析 SSE（Server-Sent Events）格式的响应
3. 当解析每个数据块时，系统应该调用提供的回调函数
4. 当流式响应完成时，系统应该返回完整的聚合响应
5. 当流式响应中断时，系统应该返回适当的错误信息

### 需求 4

**用户故事**: 作为开发者，我希望能够使用 Azure OpenAI 的嵌入模型，以便生成文本向量表示。

#### 验收标准

1. 当开发者定义嵌入器时，系统应该创建一个符合 Genkit Embedder 接口的实例
2. 当嵌入器接收请求时，系统应该调用 Azure OpenAI 的 embeddings 端点
3. 当嵌入器处理多个文本时，系统应该批量发送请求
4. 当嵌入器接收响应时，系统应该正确提取向量数据
5. 当嵌入器遇到错误时，系统应该返回描述性错误信息

### 需求 5

**用户故事**: 作为开发者，我希望插件能够正确处理消息格式转换，以便 Genkit 消息能够被 Azure OpenAI 理解。

#### 验收标准

1. 当转换用户消息时，系统应该创建包含文本和媒体内容的 Azure OpenAI 消息格式
2. 当转换系统消息时，系统应该将其放置在 input 数组的开头
3. 当转换助手消息时，系统应该包含文本内容和工具调用
4. 当转换工具响应时，系统应该使用正确的 tool_call_id 引用
5. 当消息包含图像时，系统应该支持 URL 和 base64 编码格式

### 需求 6

**用户故事**: 作为开发者，我希望插件能够处理工具调用，以便模型能够与外部函数交互。

#### 验收标准

1. 当请求包含工具定义时，系统应该将 Genkit 工具格式转换为 Azure OpenAI 格式
2. 当模型返回工具调用时，系统应该解析工具名称和参数
3. 当工具调用包含 ID 时，系统应该保留该 ID 用于后续响应
4. 当工具响应返回时，系统应该正确关联到原始工具调用
5. 当工具调用失败时，系统应该返回适当的错误信息

### 需求 7

**用户故事**: 作为开发者，我希望插件能够正确处理响应元数据，以便跟踪使用情况和调试。

#### 验收标准

1. 当接收到响应时，系统应该提取 token 使用统计信息
2. 当响应包含 finish_reason 时，系统应该将其映射到 Genkit 的 FinishReason 枚举
3. 当响应包含系统指纹时，系统应该将其存储在 custom 字段中
4. 当响应包含模型信息时，系统应该记录实际使用的模型名称
5. 当响应包含错误时，系统应该提取错误代码和消息

### 需求 8

**用户故事**: 作为开发者，我希望插件能够处理配置选项，以便自定义模型行为。

#### 验收标准

1. 当请求包含 temperature 参数时，系统应该在 API 调用中传递该参数
2. 当请求包含 max_tokens 参数时，系统应该在 API 调用中传递该参数
3. 当请求包含 top_p 参数时，系统应该在 API 调用中传递该参数
4. 当请求包含自定义配置时，系统应该支持 map[string]any 格式的配置
5. 当配置无效时，系统应该返回清晰的验证错误

### 需求 9

**用户故事**: 作为开发者，我希望插件能够参考现有的 validateAzureOpenAI 函数实现，以便了解 Azure OpenAI Responses API 的正确使用方式。

#### 验收标准

1. 当实现 HTTP 请求时，系统应该使用 /openai/responses 端点而非 /chat/completions
2. 当构建请求时，系统应该使用 input 字段而非 messages 字段（符合 Responses API 规范）
3. 当发送请求时，系统应该包含必要的认证头（api-key）
4. 当处理响应时，系统应该正确解析 Azure OpenAI 的响应格式
5. 当遇到 API 错误时，系统应该返回包含错误详情的结构化错误

### 需求 10

**用户故事**: 作为开发者，我希望插件代码结构清晰，以便维护和扩展。

#### 验收标准

1. 当查看代码时，插件应该遵循 Genkit 插件的标准接口
2. 当查看代码时，插件应该与其他 provider（如 compat_oai）保持一致的结构
3. 当查看代码时，核心逻辑应该分离到独立的文件中（如 generate.go）
4. 当查看代码时，应该包含适当的错误处理和日志记录
5. 当查看代码时，应该包含必要的文档注释和使用示例
